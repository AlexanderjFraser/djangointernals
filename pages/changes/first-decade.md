# The first decade: from a newsroom to 1.8

The decisions that shaped Django's code from its first release in 2005 to 1.8 in 2015: the magic-removal, newforms and the admin of 1.0, databases by alias, class-based views, time zones, Python 3 and the swappable user model, explicit transactions, the app registry and migrations of 1.7, and 1.8's expressions API and template engines, both designed in Django Enhancement Proposals.

Django was first released in July 2005, drawn out of a newspaper's websites (`docs/releases/1.0.txt`, `docs/faq/general.txt`; [Where Django came from, and who makes it](../introduction/origins.md)). Its first decade left marks in the code at this commit: a setting's shape, an argument that makes sense only against what came before, a comment about what is gone. The rhythm of the releases is in [What changed](../changes.md#the-releases); what followed 1.8 is [The second decade: from 1.9 to 5.0](second-decade.md).

## The magic removed

Django 0.95, released in 2006, chiefly merged a branch called magic-removal, which removed constraints on how code had to be written that "were a consequence of decisions made in the early days of Django, prior to its open-source release" (`docs/releases/0.95.txt`). Until then an application's models were "magically transferred" into Django's own namespace, django.models, and a model hooked into methods called pre_save and post_save. After it, models stayed in the module that defined them, a model overrode `Model.save` and `Model.delete` as any class overrides a method, and custom table-level functions went on a new Manager API (`django/db/models/manager.py:BaseManager`).

Two more changes of 0.95 still stand. Pieces of the framework, the template system for one, could be configured without an environment variable, to be used inside other applications, as `LazySettings.configure` allows now (`django/conf/__init__.py:LazySettings.configure`). And Django no longer required a database: a project that defines none gets a `"default"` on the dummy backend, which raises when used (`django/db/utils.py:ConnectionHandler.configure_settings`). `Model._meta` dates from the magic-removal too, say the 1.8 notes, and became an official API only in 1.8 (`docs/releases/1.8.txt`; [The options: what a model keeps as `_meta`](../models/options.md)).

## Forms rebuilt, and the admin taken out of the model

Before 0.96, [released in 2007](https://www.djangoproject.com/weblog/2007/mar/23/096/), forms were django.forms, a framework of manipulators and validation. 0.96 shipped its replacement beside it as django.newforms, copied the old one to django.oldforms, and set the schedule: the next release would move newforms to django.forms, and the one after would remove oldforms (`docs/releases/0.96.txt`).

Django 1.0, [released in September 2008](https://www.djangoproject.com/weblog/2008/sep/03/1/), made the move and rebuilt the admin on the new forms, with admin definitions "completely decoupled from model definitions (no more class Admin declaration in models!)"; the helpers form_for_model and form_for_instance gave way to `ModelForm` (`docs/releases/1.0.txt`). A model's admin options live outside it, on a `ModelAdmin`, which is registered for the model with `AdminSite.register` and builds a `ModelForm` for it (`django/contrib/admin/sites.py:AdminSite.register`, `django/contrib/admin/options.py:ModelAdmin.get_form`; [Registering models: `AdminSite.register` and `ModelAdmin`](../admin/registration.md)). The form helpers had been deprecated before 1.0 removed them; by 1.2 a deprecated feature raised a `PendingDeprecationWarning`, silent by default, then a `DeprecationWarning` in the next release, and went in the third (`docs/releases/1.0.txt`, `docs/releases/1.2.txt`; [What changed](../changes.md#how-a-change-is-carried)).

## Databases and caches by alias

Until 1.2, in 2010, a project had one database, configured by settings such as DATABASE_ENGINE and DATABASE_NAME. 1.2 replaced them with `DATABASES`, connections by alias with one named `"default"` (`docs/releases/1.2.txt`). The change reached custom fields: the methods that prepare a value gained a connection argument, since they could no longer assume the database. Preparation was split in two, `Field.get_prep_value` for every database and `Field.get_db_prep_value` for one connection, and a prepared flag tells the second whether the first has run. Both keep those signatures (`django/db/models/fields/__init__.py:Field.get_db_prep_value`).

1.3 configured caches "in the same way", by alias in `CACHES` (`docs/releases/1.3.txt`). `ConnectionHandler` and `CacheHandler` are now both subclasses of `BaseConnectionHandler` (`django/utils/connection.py:BaseConnectionHandler`; [Connections by alias: `DATABASES` and `ConnectionHandler`](../backends/connections.md)).

## Views as classes

Django's generic views were functions, in modules such as django.views.generic.list_detail. 1.3, in 2011, added class-based views, so that a view could be composed "out of a collection of methods that can be subclassed and overridden", and deprecated the functions, which 1.5 removed (`docs/releases/1.3.txt`, `docs/internals/deprecation.txt`). The URLconf did not change for them: since 0.96 a pattern could name any callable, where before it named a string (`docs/releases/0.96.txt`), and a class-based view enters it as the function `View.as_view` returns (`django/views/generic/base.py:View.as_view`; [`View.as_view` and dispatch](../views/as-view.md)).

## Time zones and the project layout

Django had used naive datetimes, "leaving it up to each developer to interpret what a given date/time 'really means'"; 1.4, in 2012, added a mode that stores datetimes in UTC, works with aware ones and converts them to the user's time zone in templates and forms, and startproject turned it on (`docs/releases/1.4.txt`). The settings startproject writes still set `USE_TZ`, true by default only since 5.0 (`docs/releases/5.0.txt`, `django/conf/project_template/project_name/settings.py-tpl`; [Time zones](../i18n/time-zones.md)).

1.4 also moved manage.py out of the project package, where its handling of import paths could import a module twice, and added `wsgi.py`, whose application the development server runs too, named by `WSGI_APPLICATION` (`docs/releases/1.4.txt`). Until 1.3 a WSGI script made a `WSGIHandler` itself. Since 1.7 that fails with `AppRegistryNotReady`: the registry of the installed applications and their models is filled by `django.setup`, and it is `get_wsgi_application` that calls `django.setup` (`docs/releases/1.7.txt`, `django/core/wsgi.py:get_wsgi_application`; [The two entry points](../handlers/entry.md)).

## Python 3, and a user model of one's own

1.5, in 2013, was "the first release with Python 3 support", one codebase for both Pythons, called experimental; 1.6 supported Python 3 officially (`docs/releases/1.5.txt`, `docs/releases/1.6.txt`). Python 2 stayed into the second decade, and loaddata still opens fixtures in binary mode, a choice its comment says may be revisited after dropping Python 2 (`django/core/management/commands/loaddata.py:Command.compression_formats`).

1.5 also let a project replace the user model, and deprecated AUTH_PROFILE_MODULE, the setting that had named a profile model for extra data (`docs/releases/1.5.txt`). `User` declares itself swappable for `AUTH_USER_MODEL`, `Options.swapped` names the model that replaces it, and code asks `get_user_model` for the one in use (`django/db/models/options.py:Options.swapped`, `django/contrib/auth/__init__.py:get_user_model`; [The user model: `AbstractBaseUser`, `User` and `AUTH_USER_MODEL`](../auth/user-model.md)).

## Transactions, made explicit

Until 1.6, in 2013, the database's own autocommit was off by default, and transactions were managed through TransactionMiddleware and decorators such as commit_on_success and commit_manually (`docs/releases/1.6.txt`, `docs/releases/1.3.txt`). 1.6 turned the database's autocommit on by default and deprecated those APIs, which 1.8 removed (`docs/releases/1.6.txt`, `docs/internals/deprecation.txt`). What stands now is `atomic`, a block that commits or rolls back and nests as savepoints (`django/db/transaction.py:Atomic`; [Transactions: autocommit, `atomic` and savepoints](../backends/transactions.md)), and a database's `"ATOMIC_REQUESTS"`, which, when true, wraps a view in one (`django/core/handlers/base.py:BaseHandler.make_view_atomic`). A `TestCase`'s tests had run in a transaction rolled back after each since 1.1 (`docs/releases/1.1.txt`); 1.8 rebuilt `TestCase` on `atomic`, one block for the class, where `TestCase.setUpTestData` runs, and one for each test (`docs/releases/1.8.txt`, `django/test/testcases.py:TestCase._enter_atomics`; [A transaction around each test: `TestCase`](../testing/test-case.md)).

## The app registry and migrations

A singleton called the app cache once held the installed applications and their models, and an application was known by its models module. 1.7, in 2014, replaced it with the app registry: an application is an `AppConfig`, which may run code at startup in `AppConfig.ready`, and every application and model is imported as Django starts (`docs/releases/1.7.txt`). That is `Apps.populate`, which `django.setup` calls (`django/apps/registry.py:Apps.populate`; [Populating the app registry](../startup/populate.md)). `Options.get_field` still uses the old name: asked for a field it cannot find among its own while the models are not ready, it says that the app cache isn't ready (`django/db/models/options.py:Options.get_field`).

The same release built in schema migrations: syncdb gave way to migrate, makemigrations writes migration files from the models, and every field must describe itself for those files through a new required method, `Field.deconstruct` (`docs/releases/1.7.txt`, `django/db/models/fields/__init__.py:Field.deconstruct`; [Migrations](../migrations.md)). syncdb survives inside migrate: with `--run-syncdb`, `Command.sync_apps` creates the tables of applications without migrations, and a test database is made with that option (`django/core/management/commands/migrate.py:Command.sync_apps`; [The migrate command, showmigrations and sqlmigrate](../migrations/migrate.md)). The 1.7 notes do not name South, [a third-party migrations application](https://www.djangoproject.com/weblog/2014/sep/02/release-17-final/); a comment does, where `MigrationQuestioner.ask_initial` looks for Python files in a migrations package before offering a first migration, to pass over South's (`django/db/migrations/questioner.py:MigrationQuestioner.ask_initial`).

## Expressions and template engines

In 2014 Django adopted a process for proposals, DEP 1, a near-copy of Python's PEPs (`deps:final/0001-dep-process.rst`; [Where Django came from, and who makes it](../introduction/origins.md#django-enhancement-proposals)). Two proposals of that year shaped 1.8, released in 2015.

### Expressions

1.1 had added aggregates, `QuerySet.aggregate` and `QuerySet.annotate`, and `F`, a reference to another field (`docs/releases/1.1.txt`). By 2014, as DEP 181 by Anssi Kääriäinen describes, an `F` expression was turned into SQL by a private, global SQLEvaluator that had to know every kind of node, and aggregates were not expressions at all, so two could not be added to each other; annotate took nothing but aggregates (`deps:final/0181-orm-expressions.rst`). The code keeps the DEP's design. An expression is bound to a query by `BaseExpression.resolve_expression` and writes its SQL with `BaseExpression.as_sql`; an `Aggregate` is a `Func` like any database function; and `F`, as the DEP proposed, is not an expression but resolves to one (`django/db/models/aggregates.py:Aggregate`, `django/db/models/expressions.py:F.resolve_expression`; [Expressions: `resolve_expression` and `as_sql`](../sql/expressions.md)). For NoSQL backends the DEP suggested a method named as_ and the vendor's name. `SQLCompiler.compile` calls such a method in place of `as_sql` where an expression has one, and Django's own expressions define such methods for its built-in backends, as `Value.as_sqlite` does (`django/db/models/sql/compiler.py:SQLCompiler.compile`, `django/db/models/expressions.py:Value.as_sqlite`).

### Template engines

Until 1.8 the one template language was configured by global settings such as TEMPLATE_DIRS. DEP 182, by Aymeric Augustin, gave convenience and speed as reasons users were turning to other engines, Jinja2 above all, and proposed a stable API for template backends, with Jinja2 built in and the Django template language kept as the default (`deps:final/0182-multiple-template-engines.rst`). `TEMPLATES` lists the engines, each a backend class named by its `"BACKEND"`, and `get_template` asks them in order until one finds the template (`django/template/loader.py:get_template`; [Template engines: `TEMPLATES` and the backends](../templates/engines.md)). Since users would have to write the new setting, the DEP proposed moving the context processors too, out of django.core, where, the DEP recalls, the magic-removal had left them; 1.8 put them in `django.template.context_processors` (`deps:final/0182-multiple-template-engines.rst`, `docs/releases/1.8.txt`).

> **Why.** DEP 182 weighed four ways of choosing an engine for a template: naming it in each call, a tag inside each template, the file's extension, and asking each engine in turn. It chose the last, keeping the first for atypical cases, and so `TEMPLATES` is a list, where `DATABASES` and `CACHES` are dictionaries: its order decides which engine wins, so a project can put replacements for an application's templates first (`deps:final/0182-multiple-template-engines.rst`).

The proposals went on after 1.8: the new middleware of 1.10 was DEP 5's, and asynchronous Django is DEP 9's (`docs/releases/1.10.txt`, `deps:accepted/0009-async.rst`), both told in [The second decade: from 1.9 to 5.0](second-decade.md).
