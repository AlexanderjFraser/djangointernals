# Language prefixes and translated routes

Language prefixes and translated routes make an address depend on the active language, which `LocaleMiddleware` chooses and makes active for a request before its path is resolved. `i18n_patterns` puts entries behind a `LocalePrefixPattern`, a matcher that reads its prefix from that language, and `translate_url` gives a page's address in another language.

A site in several languages usually wants the language in the address, `"/en/shop/"` beside `"/nl/shop/"`, and sometimes wants the words of the address translated too. Django offers the two separately, and both rest on one fact about the resolver: a matcher can ask which language is active at the moment it is used. Neither matching nor reversing is then a fixed function of the URLconf. The same path can resolve under one language and fail under another.

The examples use a second URLconf of the museum's. The entrance has one address. The opening hours and the shop are served under a language's prefix, and the route of the first is a translated string, whose Dutch translation is `"openingstijden/"`.

```python
# museum/urls_languages.py
from django.utils.translation import gettext_lazy as _

urlpatterns = [
    path("", views.entrance, name="entrance"),
] + i18n_patterns(
    path(_("opening-hours/"), views.hours, name="hours"),
    path("shop/", views.shop, name="shop"),
)
```

The figure follows one request, `GET /nl/openingstijden/`, through its stations in order, the root resolver's matcher taking the slash as it does of every path; beside it, the same path resolved while English is active. The point is the order: `LocaleMiddleware` makes Dutch active before either matcher that reads the language, the prefix or the hours' route, is asked.

## `i18n_patterns` and the prefix

`i18n_patterns` takes entries and returns a list holding one `URLResolver`. The resolver's list is those entries, and its matcher is a `LocalePrefixPattern`, the third class of matcher ([Routes, regular expressions and converters](patterns.md)). With `settings.USE_I18N` false it returns the entries as a list, with no resolver around them (`django/conf/urls/i18n.py:i18n_patterns`).

A `LocalePrefixPattern` has no text of its own. Its language prefix is worked out each time it is wanted: the code `get_language` gives for the active language, or `settings.LANGUAGE_CODE` where it gives `None`; and a slash. `LocalePrefixPattern.match` succeeds when the path begins with exactly that (`django/urls/resolvers.py:LocalePrefixPattern.language_prefix`, `django/urls/resolvers.py:LocalePrefixPattern.match`). The matcher writes itself as the same prefix, so the route on the figure's match begins with `"nl/"` (`django/urls/resolvers.py:LocalePrefixPattern.__str__`).

So the resolver that `i18n_patterns` made answers for one language at a time, the active one, and a path under any other language's prefix does not match. In the calls below, LANGUAGES is not the setting but the URLconf above, by its dotted name `"museum.urls_languages"`:

```text recording=urls
museum.urls_languages: a prefix for the active language, and a route that is translated
    with the language en active
      reverse("hours", urlconf=LANGUAGES)  ->  '/en/opening-hours/'
      reverse("shop", urlconf=LANGUAGES)  ->  '/en/shop/'
      reverse("entrance", urlconf=LANGUAGES)  ->  '/'
      resolve("/en/opening-hours/", urlconf=LANGUAGES).url_name  ->  'hours'
      resolve("/nl/openingstijden/", urlconf=LANGUAGES).url_name  ->  raises Resolver404
      resolve("/nl/opening-hours/", urlconf=LANGUAGES).url_name  ->  raises Resolver404
    with the language nl active
      reverse("hours", urlconf=LANGUAGES)  ->  '/nl/openingstijden/'
      reverse("shop", urlconf=LANGUAGES)  ->  '/nl/shop/'
      reverse("entrance", urlconf=LANGUAGES)  ->  '/'
      resolve("/en/opening-hours/", urlconf=LANGUAGES).url_name  ->  raises Resolver404
      resolve("/nl/openingstijden/", urlconf=LANGUAGES).url_name  ->  'hours'
      resolve("/nl/opening-hours/", urlconf=LANGUAGES).url_name  ->  raises Resolver404
```

The last line of the second group fails for a different reason: under Dutch the prefix is right, and the words after it are the English ones.

Reversing follows the same rule from the other side. A reversed path gets the prefix of the active language, and the entrance, which is outside `i18n_patterns`, gets none.

The prefix can be left off the default language. `i18n_patterns` takes the keyword argument `prefix_default_language=False`, and the prefix is then empty while `settings.LANGUAGE_CODE` is the active language, or none is:

```text recording=urls
UNPREFIXED is a URLconf of what i18n_patterns(path("shop/", views.shop, name="shop"), prefix_default_language=False) returns
with the language en active
  reverse("shop", urlconf=UNPREFIXED)  ->  '/shop/'
with the language nl active
  reverse("shop", urlconf=UNPREFIXED)  ->  '/nl/shop/'
  ...
```

> **Why.** `prefix_default_language=False`, the documentation says, "can be useful when adding translations to existing site so that the current URLs won't change" (`docs/topics/i18n/translation.txt`): the default language keeps the addresses it had.

## `LocaleMiddleware` and `is_language_prefix_patterns_used`

`LocaleMiddleware` chooses the request's language and activates it in its `process_request`, which runs before the handler resolves the path in `BaseHandler.resolve_request` ([Choosing a language: `LocaleMiddleware`](../i18n/choosing.md)) (`django/middleware/locale.py:LocaleMiddleware.process_request`). Something has to, since the prefix matches only the active language, and the resolver cannot, because matching the prefix is the step that needs the answer.

The middleware first asks whether the URLconf has a language prefix at all, and where it has, looks for the language in the path first. `is_language_prefix_patterns_used` goes through the entries of the root resolver's list, and no deeper, and returns two answers: whether one of them has a `LocalePrefixPattern` for its matcher, and whether that matcher gives the default language a prefix (`django/conf/urls/i18n.py:is_language_prefix_patterns_used`). For UNPREFIXED, which leaves the default language without a prefix, it answers `(True, False)`. In LANGUAGES it finds the resolver `i18n_patterns` made, and in the museum's own URLconf nothing:

```text recording=urls
is_language_prefix_patterns_used(urlconf): is there a prefix, and has the default language one
    the entry i18n_patterns made: type(entry).__name__, type(entry.pattern).__name__  ->  ('URLResolver', 'LocalePrefixPattern')
    is_language_prefix_patterns_used(LANGUAGES)  ->  (True, True)
    is_language_prefix_patterns_used("museum.urls")  ->  (False, False)
```

The function looks nowhere but in that one list, and `include` refuses, with `ImproperlyConfigured`, a URLconf one of whose entries has a `LocalePrefixPattern` (`django/urls/conf.py:include`).

Where every language has a prefix, a path with no language in it matches none of the patterns under the prefix. `LocaleMiddleware.process_response`, handed the 404, puts the active language's prefix in front of the path, asks the resolver through `is_valid_path` whether that resolves, as `CommonMiddleware` does for a missing slash, and if it does redirects to it (`django/middleware/locale.py:LocaleMiddleware.process_response`). Here the language came from the browser's header:

```text recording=urls
With LocaleMiddleware and ROOT_URLCONF = 'museum.urls_languages': GET /shop/ with Accept-Language: nl
    LocaleMiddleware.process_request
      activate('nl')
    BaseHandler.resolve_request
      URLResolver.resolve('/shop/')  (the root resolver)  raises Resolver404
    LocaleMiddleware.process_response  (given a 404)
      is_valid_path('/nl/shop/', 'museum.urls_languages')
        URLResolver.resolve('/nl/shop/')  (the root resolver)  ->  ResolverMatch(views.shop, kwargs={}, namespaces=[], route='nl/shop/')
        -> the ResolverMatch
      -> a 302, Location '/nl/shop/'
    ...
```

Without that middleware nothing activates a language from the path, and the patterns under the prefix match the prefix of the active language, `settings.LANGUAGE_CODE`'s where none is, which in a thread may be an earlier request's, since nothing deactivates it when a request ends ([The active language](../i18n/active-language.md#nothing-deactivates-at-the-end-of-a-request)).

## A route that is a translated string

The route given to `path` or `re_path` need not be a `str`. It may be the lazy string that `django.utils.translation.gettext_lazy` returns, which has no text until it is asked for some and then gives the translation for the language active at that moment.

A translated route is read in the language active at the moment a matcher needs it. Given to `path` without parameters, it is compared with what is left of the path as text, so the hours' route matches `"openingstijden/"` while Dutch is active and `"opening-hours/"` while English is (`django/urls/resolvers.py:RoutePattern.match`). Its regular expression, which reversing reads for every entry, is kept for each language (`django/urls/resolvers.py:URLResolver._populate`). The descriptor behind `regex` ([When a matcher's expression is compiled](patterns.md#when-a-matchers-expression-is-compiled)) expands the route's text under the active language, compiles it, and keeps the result in the matcher's `_regex_dict` under the language's code, so a read under another language does all of that again (`django/urls/resolvers.py:LocaleRegexRouteDescriptor`). `RegexPattern` has a descriptor of the same design (`django/urls/resolvers.py:LocaleRegexDescriptor`).

The shop's matcher, its route a `str`, has its one compiled expression on itself and nothing in `_regex_dict`; the hours' matcher has nothing on itself, and an expression in `_regex_dict` for each of the two languages the tables for reversing have been built under:

```text recording=urls
What is kept once, and what once for each language
    shop is the URLPattern of the route "shop/", a str; hours is the URLPattern of the translated route; resolver is the root resolver of museum.urls_languages
    type(shop.pattern._route).__name__  ->  'str'
    "regex" in vars(shop.pattern)  ->  True
    sorted(shop.pattern._regex_dict)  ->  []
    type(hours.pattern._route).__mro__[1].__name__  ->  'Promise'
    "regex" in vars(hours.pattern)  ->  False
    sorted(hours.pattern._regex_dict)  ->  ['en', 'nl']
    ...
```

> **Trap.** A translation has to keep the route's parameters, and change only the words between them. A `RoutePattern` takes its converters once, as it is made, from the route's text in the language active as the URLconf is imported, and `RoutePattern.match` looks up by name the converter of each group that the active language's expression captured (`django/urls/resolvers.py:RoutePattern.__init__`, `django/urls/resolvers.py:RoutePattern.match`). Where the Dutch catalogue translates `"visits/<int:year>/"` as `"bezoeken/<int:jaar>/"` and the URLconf was imported under English, the converters name only year, resolving `"/nl/bezoeken/2026/"` under Dutch raises `KeyError: 'jaar'` out of `RoutePattern.match`, and a request for it is answered with a 500, not a 404.

## Tables for each language

Reversing depends on the language too, and the tables of [Reversing a name](reversing.md#the-tables) are built from regular expressions, so there cannot be one set of them. Each of a resolver's three dictionaries is a dictionary of dictionaries, keyed first by language code. `URLResolver._populate` files what it builds under the language that is active as it runs, and each of the three properties that read them calls it again when the active language has no entry yet (`django/urls/resolvers.py:URLResolver._populate`, `django/urls/resolvers.py:URLResolver.reverse_dict`). Once the museum's names have been reversed under both languages, the root resolver's `_reverse_dict` holds a table under `"en"` and another under `"nl"`.

The first reverse under each language therefore pays for a pass over the whole tree, and a process keeps a copy of its tables for each language it has reversed under. In each copy, a form that came from under `i18n_patterns` begins with the language prefix of that copy's language.

## `translate_url`

`translate_url` is given a URL and a language code and returns the address of the same page in that language. It takes the URL's path, decodes its percent escapes, and resolves it under the language now active, to learn which pattern serves it and with what arguments. Then, with the language asked for active only while it does so, it reverses that pattern's name, namespaces included, with the same arguments. The scheme, host, query string and fragment of the URL it was given are put back around the new path (`django/urls/base.py:translate_url`). It returns the URL unchanged when the path does not resolve or the name cannot be reversed.

Three of the answers below are the URL as it was given, each for its own reason: `"/en/nothing/"` resolves to nothing; the entrance resolves and reverses, and its address is the same in both languages; and the Dutch address handed in while English is active is the one the Trap explains:

```text recording=urls
translate_url(url, lang_code): the same view's address in another language
    with en active, and museum.urls_languages the current URLconf
      translate_url("/en/opening-hours/", "nl")  ->  '/nl/openingstijden/'
      translate_url("https://museum.example/en/opening-hours/?day=sunday#top", "nl")  ->  'https://museum.example/nl/openingstijden/?day=sunday#top'
      ...
      translate_url("/", "nl")  ->  '/'
      translate_url("/en/nothing/", "nl")  ->  '/en/nothing/'
      translate_url("/nl/openingstijden/", "en")  ->  '/nl/openingstijden/'
    with nl active
      translate_url("/nl/openingstijden/", "en")  ->  '/en/opening-hours/'
```

> **Trap.** `translate_url` translates only an address in the language active when it is called. It resolves the path before it activates the language it was asked for, so a Dutch address handed in while English is active does not resolve, and comes back untranslated (`django/urls/base.py:translate_url`).

Its one caller in Django is the view `set_language`, which redirects a visitor who has chosen a language to the page's address in that language ([The language views: `set_language` and `JavaScriptCatalog`](../i18n/views.md)) (`django/views/i18n.py:set_language`).
